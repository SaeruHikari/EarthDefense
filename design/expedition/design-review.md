# 二阶段远征设计一致性审查

审查范围：proposal.md、world-and-combat.md、save-audit.md；数值细案完成后，追加了 progression-balance.md 的节点计数、旧 ID 映射、预算和关键前置口径检查。以下保留第一轮具体修改建议与最终复核结果。主任务已按建议修正文档；本审查仅依明确授权补充 save-audit 的阶段标志，未修改生产代码或真实存档，未运行游戏。行号指初审版本，正文修改后可能移动。

## 第一轮发现与已采纳修改

### R1 / 已解决：区分历史波次与远征局部波次

位置：proposal.md 第 6、10 节；world-and-combat.md 第 3 节。

真实存档 `wave=125`、`completed_waves=125`、`defense_time≈6495.94s`，新远征每战区只有 6 个普通波。如果继续把原 `game.wave` 代入基础刷怪公式，第一站可能从第 126 波数量起步；如果直接重置原字段，又会破坏继承统计与旧科技门槛。旧敌弹成长也会因已超过 630 秒而处于最大弹量。

建议明确三组独立数据：`earth_history.wave/completed_waves/defense_time` 原样保留；`expedition_run.wave_index` 从 1 至 6；`expedition_run.elapsed` 从本次出发开始，承担明确选定的远征弹量成长计时。旧 28 项参数保留原值，但作用时必须指定阶段和变量，不能仅靠字段名复用。出征与载入均保存当前局部快照，不能为了降低难度清掉原历史。

### R2 / 已解决：战斗中“自动保存当前工作档”可能制造伪安全点

位置：proposal.md 第 8 节，原第 126 行。

“载入先自动保存当前工作档”若在战斗中直接调用当前单文件保存，会保存已增加的 game.wave/部分资产，却丢失 enemies、刷怪 elapsed、将军阶段等状态；新记录可能跳过未完成的战斗或部分结算奖励。这与当前仅支持战略 checkpoint 的限制冲突。

建议：战略安全态先提交修订；战斗态只保留最近已验证安全点，并明确本次未结算进度会被放弃，或允许等到结算后再加载。只有完整 battle_snapshot 合同上线后才提供“保存现场再加载”。不要把当前内存的局部字段写成新的 strategic_checkpoint。

### R3 / 已解决：首战失败不能只依赖“已占领低级复战”恢复

位置：world-and-combat.md 第 2、5 节；proposal.md 第 2、6 节。

首舰启动静态预算可支付，但支出后合金只有 150。玩家尚未占领任何星球就失败时，没有可用的已占领复战。若修理、重新出发或恢复精炼线还需更多合金，会违背“失败可恢复”。现文只规定恢复不能死锁，没有给出最低可执行路径。

建议在数值细案给出确定的保底合同：舰体/预装基础工厂保留；允许免费时间修复或仅用地球可再生产资源修复；从无新材料状态也能启动精炼；未占领星球首次失败后能用同一最低配置再次出航。分清母舰本体、甲板模块、已研发蓝图、工厂核心强化和未结算货舱的损失范围，不将永久核心投资或已支付舰体重新收费。

### R4 / 已解决：将军与母舰同一模拟步死亡时，结算顺序须固定

位置：world-and-combat.md 第 2、3、4 节。

当前一处说母舰击毁自动撤离、未完成战区不计占领；另一处说将军击败、核心/协议/占领为同一事件。双方在 AOE/派生伤害同一步死亡时，若按节点遍历先后处理，会出现已发核心未占领、已占领却掉落丢失，或同场结果因刷新次序改变。

建议先收集该模拟步死亡事件再做一次 RunSettlement：明确“将军合法死亡优先认定胜利并原子结算，随后母舰撤离修理”或其它统一规则。占领 ID、核心、协议、普通货舱归属、n 的变化和结算状态一起提交；重复回调/载入不再发奖。结算后永久蓝图与已入账核心不按未运回普通货舱丢弃。

### R5 / 已解决：首次战区不能使用复战的可选低威胁值

位置：proposal.md 第 6 节；world-and-combat.md 第 5 节。

当前设计已用将军击败与首次占领绑定，堵住“先拿六个协议再点占领”的主要绕过。还应约束战区入场参数：未占领战区 `threat_snapshot = conquered_unique_count`，不接受 UI 提交的复战等级；已占领才可选择复战等级，敌人和奖励都用该实际等级。

建议将“首次/复战”由合法占领集合推导，不信任保存的独立 bool；离开未完成战场后清除该 run 的锁定威胁，再次出发使用当时合法 n。不能先把六个未占领战区各建立 n=0 挂起实例，再逐个低难度通关。单精确战场之外，也要明确是否保存多个待续 run；初版建议最多一个。

### R6 / 已解决：主辅协议验收表统一为 90 个有向配置

位置：proposal.md M5 表与其后说明。

当前 M5 表写 45 个组合，而正文又正确说明主辅效果不同必须检查 90。建议发布门槛直接写 `6×5×3=90` 个有向主辅/机型配置，`C(6,2)×3=45` 只作为去重后的基础兼容检查。明确主辅不可相同，否则如果允许自身配对需改为 `6×6×3=108`；这也应反映在装配 UI 校验中。
